ETAPA 1: Introducción

GitHub - ¿Qué es y para qué sirve?

GitHub es una plataforma en línea que permite alojar repositorios Git y trabajar de forma colaborativa en proyectos de software. Mientras Git se encarga de controlar las versiones de un proyecto de manera local, GitHub permite almacenar esos repositorios en la nube, compartirlos y colaborar con otros desarrolladores.

  1. Se utiliza normalmente para guardar una copia remota de un repositorio Git y tener el proyecto disponible en línea.
  2. Permite colaborar con otros desarrolladores mediante ramas, Pull Requests, revisiones de código e incidencias (Issues).
  3. Para comenzar, creá una cuenta en GitHub y luego creá un repositorio remoto desde la plataforma.
  4. Conectá tu repositorio local con GitHub utilizando git remote add origin URL_DEL_REPOSITORIO.
  5. Finalmente, enviá tus commits al repositorio remoto utilizando git push -u origin main.

Beneficios

GitHub se utiliza en proyectos personales, equipos de desarrollo, empresas y proyectos de código abierto. Además de almacenar repositorios Git, permite colaborar, revisar código, gestionar tareas y publicar proyectos.

  1. Guardar proyectos: podés subir un proyecto desarrollado en tu computadora para tener una copia remota y acceder a él desde diferentes dispositivos.
  2. Trabajar en equipo: varios desarrolladores pueden trabajar sobre el mismo proyecto mediante ramas, commits y Pull Requests.
  3. Participar en proyectos de código abierto: permite consultar proyectos públicos, realizar un fork, crear cambios y proponerlos al proyecto original mediante un Pull Request.
  4. Gestionar tareas y errores: las herramientas como Issues permiten registrar problemas, solicitudes de funcionalidades y tareas pendientes.
  5. Revisar código: los Pull Requests permiten que otros desarrolladores revisen los cambios antes de incorporarlos a una rama principal.
  6. Crear un portfolio: los desarrolladores pueden utilizar sus repositorios públicos para mostrar proyectos y conocimientos técnicos.
  7. Automatizar procesos: GitHub Actions permite ejecutar tareas automáticamente, como pruebas, análisis de código o procesos de despliegue.
  8. Publicar sitios web: mediante GitHub Pages es posible publicar determinados proyectos y sitios web directamente desde un repositorio.

Ejemplo de uso real

Supongamos que trabajás como desarrollador en una empresa y formás parte de un equipo que está construyendo una aplicación web. Diferentes desarrolladores trabajan al mismo tiempo en distintas partes del proyecto. En este escenario, Git y GitHub permiten organizar el trabajo y evitar que los cambios de un desarrollador sobrescriban los de otro.

  1. Crear el repositorio: el equipo crea un repositorio en GitHub donde se almacena el código del proyecto y se centraliza el trabajo.
  2. Trabajar con ramas: cada desarrollador crea una rama para trabajar de forma independiente. Por ejemplo, login para desarrollar el sistema de inicio de sesión o carrito-compras para implementar el carrito.
  3. Realizar commits: cada desarrollador guarda sus avances mediante commits descriptivos, manteniendo un historial de todos los cambios realizados.
  4. Subir los cambios a GitHub: cuando termina una parte del trabajo, utiliza git push para enviar su rama al repositorio remoto.
  5. Crear un Pull Request: el desarrollador solicita incorporar sus cambios a la rama principal. Otros integrantes del equipo pueden revisar el código antes de aprobarlo.
  6. Resolver conflictos: si dos desarrolladores modificaron la misma parte del código, Git puede detectar un conflicto que deberá resolverse antes de completar la integración.
  7. Fusionar los cambios: una vez revisado y aprobado el código, la rama se integra con main mediante un merge.
  8. Continuar el desarrollo: el resto del equipo puede obtener los nuevos cambios utilizando git pull y continuar trabajando sobre la versión actualizada del proyecto.

Git vs GitHub

Git y GitHub no son lo mismo, aunque están estrechamente relacionados. Git es el sistema de control de versiones que permite gestionar los cambios de un proyecto, mientras que GitHub es una plataforma en línea que permite alojar repositorios Git y facilitar la colaboración entre desarrolladores.

  1. Git: es un programa que se instala en tu computadora y permite crear repositorios, realizar commits, trabajar con ramas, comparar cambios y consultar el historial del proyecto.
  2. GitHub: es un servicio en línea donde podés almacenar repositorios Git, compartirlos y trabajar colaborativamente con otros desarrolladores.
  3. Git funciona localmente: podés utilizar Git sin conexión a Internet para controlar las versiones de tus proyectos.
  4. GitHub funciona de forma remota: necesitás una conexión para enviar o recibir información del repositorio remoto, por ejemplo mediante git push y git pull.
  5. Trabajan juntos: Git administra el historial y las versiones en tu computadora, mientras que GitHub puede almacenar una copia remota y proporcionar herramientas para colaborar con otros desarrolladores.

Flujo de trabajo

El flujo de trabajo básico de GitHub consiste en conectar un repositorio local de Git con un repositorio remoto en GitHub para poder desarrollar, guardar y compartir los cambios realizados en un proyecto.

  1. Crear o clonar el repositorio: podés crear un proyecto local con git init o descargar uno existente desde GitHub utilizando git clone.
  2. Crear una rama: para trabajar en una nueva funcionalidad o corrección, creá una rama independiente utilizando git switch -c nombre-rama.
  3. Modificar los archivos: realizá los cambios necesarios en el proyecto desde tu editor de código, como Visual Studio Code.
  4. Revisar los cambios: utilizá git status y git diff para comprobar qué archivos fueron modificados y qué cambios realizaste.
  5. Preparar los archivos: agregá los cambios al Staging Area mediante git add nombre-archivo o git add ..
  6. Crear un commit: guardá los cambios en el historial local utilizando git commit -m "Descripción de los cambios".
  7. Subir la rama a GitHub: enviá los commits al repositorio remoto mediante git push -u origin nombre-rama.
  8. Crear un Pull Request: desde GitHub, solicitá la revisión de los cambios para que otros integrantes del equipo puedan analizarlos antes de incorporarlos a main.
  9. Fusionar los cambios: una vez aprobados, los cambios pueden integrarse a la rama principal mediante un merge.
  10. Actualizar el repositorio local: obtené los últimos cambios realizados por el equipo con git pull antes de continuar trabajando.

ETAPA 2: Crear cuenta

Crear una cuenta paso a paso

Para comenzar a utilizar GitHub necesitás crear una cuenta gratuita. Con ella podrás crear repositorios, guardar proyectos, colaborar con otros desarrolladores y utilizar las herramientas de GitHub.

  1. Ingresá al sitio oficial de GitHub y seleccioná la opción Sign up para crear una nueva cuenta.
  2. Ingresá tu correo electrónico, establecé una contraseña segura y elegí un nombre de usuario que utilizarás para identificarte en GitHub.
  3. Completá el proceso de verificación solicitado por GitHub para confirmar que sos una persona real.
  4. Revisá tu correo electrónico y verificá tu dirección de email siguiendo las instrucciones recibidas.
  5. Completá las opciones de configuración inicial que GitHub pueda mostrarte, como tus preferencias o características que quieras utilizar.
  6. Una vez finalizado el registro, iniciá sesión y accederás a tu cuenta de GitHub.
  7. Desde tu cuenta ya podrás crear tu primer repositorio utilizando el botón New o Create repository.

Configuración inicial

Después de crear una cuenta en GitHub, es recomendable realizar algunas configuraciones iniciales para trabajar de forma segura, organizada y profesional. Estas opciones permiten proteger la cuenta, identificar correctamente tus contribuciones y preparar el entorno para trabajar con repositorios.

  1. Verificar el correo electrónico: confirmá tu dirección de email desde el mensaje enviado por GitHub. Esto permite utilizar correctamente diferentes funciones de la plataforma y asociar tus commits con tu cuenta.
  2. Configurar la autenticación en dos pasos (2FA): activá la autenticación de dos factores desde la configuración de seguridad de GitHub. Esto agrega una capa adicional de protección además de la contraseña.
  3. Configurar tu perfil: agregá un nombre, fotografía, biografía y, si corresponde, información sobre tus conocimientos o proyectos. Un perfil bien configurado resulta especialmente útil cuando utilizás GitHub como portfolio profesional.
  4. Configurar una dirección de email para los commits: asegurate de utilizar en Git el mismo correo electrónico asociado a tu cuenta de GitHub, o una dirección proporcionada por GitHub para mantener tu privacidad. Podés configurarlo con: git config --global user.email "tu-correo@example.com".
  5. Configurar la autenticación con Git: para trabajar desde la terminal con repositorios privados o realizar operaciones como git push, configurá un método de autenticación. Actualmente se recomienda utilizar SSH o herramientas de autenticación compatibles con GitHub en lugar de utilizar una contraseña tradicional.
  6. Configurar una clave SSH: una clave SSH permite autenticar tu computadora con GitHub y trabajar con repositorios sin tener que introducir credenciales constantemente. Después de configurarla, podés utilizar una URL SSH como git@github.com:usuario/repositorio.git.
  7. Revisar las opciones de notificaciones: configurá qué notificaciones querés recibir para evitar recibir información innecesaria y mantener organizados los avisos relacionados con repositorios, Issues y Pull Requests.
  8. Conocer la configuración de repositorios: familiarizate con opciones como colaboradores, permisos, ramas protegidas y reglas del repositorio, especialmente cuando comiences a trabajar en proyectos de equipo.
  9. Configurar GitHub CLI (opcional): si trabajás habitualmente desde la terminal, gh permite interactuar con GitHub desde la línea de comandos, por ejemplo para crear repositorios, consultar Issues o administrar Pull Requests.

Configuración mínima recomendada: verificá tu email, activá 2FA, completá tu perfil, configurá correctamente el email utilizado por Git y establecé un método seguro de autenticación, preferentemente SSH para trabajar desde tu computadora.

Conociendo la interfaz

La interfaz de GitHub permite administrar repositorios, consultar archivos, revisar commits, trabajar con ramas, crear Pull Requests y colaborar con otros desarrolladores. Es importante conocer sus principales secciones y relacionarlas con los comandos de Git que utilizamos desde la terminal.

  1. Code: permite acceder a los archivos del repositorio, consultar las ramas disponibles, copiar la URL del repositorio y descargar o clonar el proyecto.
  2. Issues: permite registrar errores, tareas, problemas y nuevas funcionalidades que deben resolverse dentro del proyecto.
  3. Pull requests: permite proponer cambios realizados en una rama para que otros integrantes del equipo puedan revisarlos antes de incorporarlos a otra rama.
  4. Actions: permite automatizar tareas mediante GitHub Actions, como ejecutar pruebas, analizar código o realizar procesos de despliegue.
  5. Settings: permite configurar diferentes aspectos del repositorio, como colaboradores, permisos, ramas y otras opciones.
  6. Commits: desde el historial del repositorio podés consultar los commits realizados, incluyendo su mensaje, autor y cambios asociados.
  7. Branches: permite consultar las diferentes ramas existentes en el repositorio y conocer cuál es la rama principal del proyecto.
  8. README: normalmente se utiliza para explicar qué hace el proyecto, cómo instalarlo, cómo utilizarlo y cualquier otra información importante.
  9. Releases: permite publicar versiones específicas del proyecto utilizando etiquetas (git tag), por ejemplo v1.0.0.
  10. Clone: desde el botón Code podés obtener la dirección del repositorio para clonarlo en tu computadora mediante git clone URL_DEL_REPOSITORIO.

Comandos que debés conocer para trabajar con GitHub:

  • git clone → descarga un repositorio de GitHub a tu computadora.
  • git remote → permite consultar o administrar la conexión con el repositorio remoto.
  • git push → envía commits desde tu repositorio local hacia GitHub.
  • git pull → obtiene cambios de GitHub y los integra en tu rama local.
  • git fetch → descarga información del repositorio remoto sin integrar automáticamente los cambios.
  • git branch → permite crear, consultar y administrar ramas.
  • git switch → permite cambiar de una rama a otra.
  • git merge → permite fusionar los cambios de una rama con otra.

El flujo básico para trabajar con GitHub desde la terminal suele ser: git clone → modificar archivos → git add → git commit → git push. Para obtener cambios realizados por otros integrantes, normalmente utilizaremos git pull.

ETAPA 2: Repositorio

¿Qué es un repositorio?

Un repositorio en GitHub es un espacio donde se almacena un proyecto y toda la información relacionada con su desarrollo. Puede contener archivos de código, documentación, imágenes, commits, ramas y otros elementos necesarios para gestionar y colaborar en el proyecto.

  1. Almacena el proyecto: contiene los archivos y carpetas que forman parte de la aplicación, sitio web o proyecto.
  2. Guarda el historial: los commits permiten consultar cómo fue evolucionando el proyecto y conocer los cambios realizados.
  3. Permite trabajar con ramas: cada desarrollador puede crear ramas para desarrollar nuevas funcionalidades o realizar correcciones sin modificar directamente la rama principal.
  4. Facilita la colaboración: varios desarrolladores pueden trabajar sobre el mismo repositorio utilizando Pull Requests, Issues y revisiones de código.
  5. Puede ser público o privado: un repositorio público puede ser consultado por otras personas, mientras que uno privado limita el acceso a los usuarios autorizados.
  6. Puede conectarse con un repositorio local: mediante comandos como git remote add, git push y git pull es posible sincronizar el repositorio de tu computadora con el repositorio alojado en GitHub.

Por ejemplo, si tenés un proyecto llamado mi-sitio-web, podés crear un repositorio con ese nombre en GitHub y utilizarlo como repositorio remoto para almacenar y compartir el código de tu proyecto.

Crear un repositorio paso a paso

Crear un repositorio en GitHub permite alojar un proyecto de forma remota y conectarlo posteriormente con el repositorio Git de tu computadora. Es uno de los primeros pasos para comenzar a trabajar con GitHub.

  1. Iniciá sesión en tu cuenta de GitHub.
  2. En la parte superior de GitHub, seleccioná + y luego New repository.
  3. En Repository name, escribí el nombre que tendrá tu repositorio, por ejemplo mi-proyecto.
  4. Si querés, agregá una descripción breve para explicar cuál es el objetivo del proyecto.
  5. Elegí la visibilidad del repositorio:
    • Public: cualquier persona puede consultar el repositorio.
    • Private: solamente vos y las personas autorizadas podrán acceder.
  6. Podés seleccionar Add a README file si querés que GitHub cree automáticamente un archivo README.md para documentar el proyecto.
  7. Si el proyecto ya existe en tu computadora y vas a conectarlo con este repositorio, evitá agregar inicialmente archivos como README, .gitignore o licencia para mantener el repositorio remoto vacío y evitar conflictos al realizar la primera sincronización.
  8. Seleccioná Create repository para crear el repositorio.
  9. Una vez creado, GitHub mostrará la dirección del repositorio. Podrás utilizarla para conectar tu proyecto local con GitHub mediante git remote add origin URL_DEL_REPOSITORIO.
  10. Finalmente, podés enviar tu proyecto local a GitHub utilizando git push -u origin main.

Cómo conectar un repositorio local con GitHub

Conectar un repositorio local con GitHub permite vincular el proyecto que tenés en tu computadora con un repositorio remoto. De esta manera, podés enviar tus commits a GitHub mediante git push y obtener posteriormente los cambios realizados desde otros equipos o por otros integrantes del proyecto.

  1. Creá un repositorio en GitHub: primero creá un repositorio remoto desde tu cuenta de GitHub. Si ya tenés un proyecto local con commits, es recomendable crear el repositorio remoto vacío, sin agregar inicialmente un README.
  2. Abrí la terminal en tu proyecto: ubicá la terminal dentro de la carpeta que contiene tu proyecto local.
  3. Verificá que sea un repositorio Git: ejecutá git status. Si todavía no lo inicializaste, utilizá git init.
  4. Agregá el repositorio remoto: ejecutá git remote add origin URL_DEL_REPOSITORIO. La palabra origin será el nombre utilizado habitualmente para identificar el repositorio remoto.
  5. Verificá la conexión: ejecutá git remote -v. Git mostrará las direcciones utilizadas para obtener y enviar información al repositorio remoto.
  6. Verificá el nombre de tu rama principal: podés utilizar git branch. Si tu rama principal se llama main, continuarás utilizando ese nombre en los siguientes comandos.
  7. Enviá los commits a GitHub: ejecutá git push -u origin main. La opción -u establece la relación entre tu rama local main y la rama remota correspondiente.
  8. Comprobá el resultado: actualizá la página del repositorio en GitHub y verificá que los archivos y commits de tu proyecto local aparezcan en el repositorio remoto.

Flujo básico: git init → git add . → git commit → git remote add origin URL → git push -u origin main.

README.md – Documentar un proyecto

El archivo README.md es el documento principal de un repositorio y se utiliza para explicar qué es el proyecto, para qué sirve, cómo instalarlo y cómo utilizarlo. GitHub muestra automáticamente este archivo en la página principal del repositorio.

  1. Creá el archivo: dentro de la carpeta principal del proyecto, creá un archivo llamado README.md.
  2. Agregá una descripción: explicá brevemente qué hace el proyecto y cuál es su objetivo.
  3. Documentá la instalación: indicá los requisitos necesarios y los pasos que debe seguir otra persona para instalar y ejecutar el proyecto.
  4. Explicá cómo utilizarlo: agregá ejemplos de uso, comandos importantes o instrucciones necesarias para comenzar a trabajar con el proyecto.
  5. Documentá las tecnologías: indicá qué lenguajes, frameworks, bibliotecas o herramientas fueron utilizadas para desarrollar el proyecto.
  6. Agregá información adicional: dependiendo del proyecto, podés incluir características principales, capturas de pantalla, estructura de carpetas, configuración, licencia, autores y formas de contacto.
  7. Guardá el README en Git: agregalo al Staging Area utilizando git add README.md y luego creá un commit con git commit -m "Agregar documentación del proyecto".
  8. Subilo a GitHub: enviá el commit mediante git push. GitHub mostrará automáticamente el contenido del README.md en la página principal del repositorio.

Estructura recomendada:

  • # Nombre del proyecto → título principal.
  • ## Descripción → explicación del proyecto.
  • ## Características → funcionalidades principales.
  • ## Tecnologías utilizadas → herramientas y tecnologías.
  • ## Instalación → pasos para instalarlo.
  • ## Uso → instrucciones y ejemplos.
  • ## Capturas de pantalla → imágenes del proyecto, si corresponde.
  • ## Autor → información del desarrollador.
  • ## Licencia → licencia utilizada por el proyecto.

Un buen README.md es especialmente importante en proyectos profesionales y de código abierto porque permite que otra persona pueda comprender rápidamente el proyecto, instalarlo y comenzar a utilizarlo sin necesidad de preguntarle al desarrollador cómo funciona.

ETAPA 2: Git + GitHub

Git push – Subir cambios a GitHub

git push es el comando que permite enviar los commits de un repositorio local hacia un repositorio remoto, como GitHub. Es fundamental para compartir tu trabajo, realizar copias remotas del proyecto y permitir que otros integrantes del equipo puedan acceder a tus cambios.

  1. Verificá el estado del proyecto: antes de subir cambios, ejecutá git status para comprobar qué archivos fueron modificados y en qué estado se encuentran.
  2. Revisá los cambios: utilizá git diff para comprobar exactamente qué líneas fueron modificadas antes de guardarlas en un commit.
  3. Agregá los archivos al Staging Area: utilizá git add nombre-archivo para agregar un archivo específico o git add . para agregar todos los cambios.
  4. Creá un commit: guardá los cambios en el historial local mediante git commit -m "Descripción de los cambios".
  5. Verificá el repositorio remoto: ejecutá git remote -v para comprobar que tu repositorio local está conectado correctamente con GitHub.
  6. Subí los cambios: utilizá git push origin main para enviar los commits de tu rama local main hacia la rama main del repositorio remoto.
  7. Configurá el seguimiento de la rama: cuando realizás el primer envío de una rama podés utilizar git push -u origin main. La opción -u establece una relación entre la rama local y la rama remota.
  8. Realizá futuros push: después de establecer el seguimiento, normalmente será suficiente utilizar git push para enviar los nuevos commits a GitHub.

Ejemplo completo:

  1. Modificás index.html.
  2. Comprobás los cambios con git status y git diff.
  3. Preparás el archivo con git add index.html.
  4. Creás el commit con git commit -m "Actualizar página principal".
  5. Subís el commit con git push.

Flujo básico: Modificar → git status → git diff → git add → git commit → git push.

¿Qué hace realmente git push? El comando no sube simplemente archivos individuales. Git envía al repositorio remoto los commits que todavía no están allí y actualiza la referencia de la rama remota. Por eso, antes de utilizar git push, los cambios deben haber sido guardados previamente mediante uno o varios commits.

Subir una rama diferente: si estás trabajando en una rama llamada login, podés enviarla a GitHub utilizando git push -u origin login. Esto permite que la rama también exista en el repositorio remoto y pueda utilizarse posteriormente para crear un Pull Request.

Ver las ramas remotas: podés utilizar git branch -r para consultar las ramas remotas conocidas por tu repositorio local.

Importante: git push normalmente no debe utilizarse para sobrescribir el trabajo de otros integrantes. Si el repositorio remoto contiene cambios que todavía no tenés localmente, Git puede rechazar el envío. En ese caso, primero deberás obtener y revisar los cambios remotos, normalmente mediante git pull o utilizando un flujo basado en git fetch.

Git clone – Descargar un repositorio de GitHub

git clone es el comando que permite copiar un repositorio remoto, como uno alojado en GitHub, a tu computadora. No solo descarga los archivos del proyecto, sino también su historial de commits, ramas y la configuración necesaria para establecer la conexión con el repositorio remoto.

  1. Obtené la URL del repositorio: ingresá al repositorio de GitHub que querés descargar y seleccioná el botón Code. Allí podrás copiar su dirección mediante HTTPS o SSH.
  2. Abrí la terminal: abrí Git Bash o la terminal integrada de Visual Studio Code y ubicáte en la carpeta donde querés guardar el proyecto.
  3. Cloná el repositorio: ejecutá git clone URL_DEL_REPOSITORIO. Git creará automáticamente una carpeta con el nombre del repositorio y descargará su contenido.
  4. Entrá en la carpeta: utilizá cd nombre-del-repositorio para ingresar al proyecto recién descargado.
  5. Verificá el repositorio: ejecutá git status para comprobar que el proyecto fue clonado correctamente.
  6. Verificá el repositorio remoto: utilizá git remote -v. Git debería mostrar la dirección de GitHub asociada al repositorio remoto, normalmente identificada como origin.

Ejemplo utilizando HTTPS:

git clone https://github.com/usuario/mi-proyecto.git

Ejemplo utilizando SSH:

git clone git@github.com:usuario/mi-proyecto.git

¿Qué ocurre después de ejecutar git clone? Git crea una copia local del repositorio y configura automáticamente el repositorio remoto como origin. Además, descarga los commits y la información necesaria para que puedas continuar trabajando con Git desde tu computadora.

Después de clonar: normalmente podés abrir el proyecto en Visual Studio Code, crear una nueva rama, modificar los archivos, realizar commits y enviar tus cambios nuevamente a GitHub mediante git push.

Flujo básico: GitHub → Code → Copiar URL → git clone → cd proyecto → git status → trabajar → git add → git commit → git push.

¿Cuándo se utiliza? Es especialmente útil cuando comenzás a trabajar en un proyecto que ya existe en GitHub, cuando te incorporás a un equipo de desarrollo o cuando necesitás obtener una copia del proyecto en otra computadora.

Importante: git clone se utiliza normalmente para obtener un repositorio por primera vez. Si ya tenés el repositorio clonado y simplemente querés obtener los cambios más recientes realizados por otros integrantes, normalmente utilizarás git pull en lugar de volver a ejecutar git clone.

Git pull – Actualizar un proyecto desde GitHub

git pull es el comando que permite obtener los cambios realizados en un repositorio remoto, como GitHub, e incorporarlos a tu repositorio local. Es fundamental cuando trabajás en equipo y otros desarrolladores han enviado nuevos commits al repositorio remoto.

  1. Ubicate en tu proyecto: abrí Git Bash o la terminal de Visual Studio Code y entrá en la carpeta del repositorio utilizando cd nombre-del-repositorio.
  2. Verificá el estado actual: ejecutá git status para comprobar si tenés cambios locales pendientes antes de actualizar el proyecto.
  3. Comprobá la rama actual: utilizá git branch para verificar en qué rama estás trabajando. Si querés actualizar main, asegurate de encontrarte en esa rama.
  4. Obtené e integrá los cambios: ejecutá git pull. Git descargará los cambios del repositorio remoto y los integrará en tu rama local.
  5. Verificá el resultado: utilizá nuevamente git status y, si es necesario, git log --oneline para comprobar que tu repositorio local quedó actualizado.

Ejemplo básico:

git pull

También podés indicar explícitamente el repositorio remoto y la rama que querés actualizar:

git pull origin main

¿Qué hace realmente git pull? Conceptualmente, git pull combina dos operaciones: primero obtiene información y commits nuevos del repositorio remoto y después intenta integrarlos en tu rama local. Por eso, si existen cambios locales incompatibles con los cambios remotos, Git puede solicitar que resuelvas un conflicto.

¿Cuándo se utiliza? Es especialmente importante en equipos de desarrollo. Por ejemplo, si otro integrante del equipo modificó el proyecto y ejecutó git push, vos podés ejecutar git pull para obtener esos cambios y continuar trabajando sobre la versión más reciente.

Ejemplo de trabajo en equipo:

  1. Un desarrollador modifica el proyecto y crea un commit.
  2. Ejecuta git push y envía sus cambios a GitHub.
  3. Otro desarrollador, que tiene una copia local del mismo repositorio, ejecuta git pull.
  4. Git descarga los nuevos commits e intenta integrarlos en su rama local.
  5. El segundo desarrollador puede continuar trabajando sobre la versión actualizada.

¿Qué ocurre si hay conflictos? Si tus cambios locales entran en conflicto con los cambios que vienen desde GitHub, Git puede detener la integración y solicitar que resuelvas manualmente los archivos afectados. Después de solucionar los conflictos, deberás preparar los archivos con git add y completar la integración según el estado indicado por Git.

git pull vs git clone: git clone se utiliza normalmente para descargar un repositorio por primera vez. En cambio, git pull se utiliza cuando ya tenés el repositorio en tu computadora y querés actualizarlo con los cambios disponibles en GitHub.

Flujo habitual: git pull → modificar → git add → git commit → git push. En un equipo de trabajo, es habitual actualizar primero el repositorio antes de comenzar una nueva tarea para reducir la posibilidad de trabajar sobre una versión desactualizada.

Git fetch – Consultar cambios remotos

git fetch permite consultar y descargar información nueva desde un repositorio remoto, como GitHub, sin modificar automáticamente los archivos de tu proyecto ni integrar esos cambios en la rama en la que estás trabajando. Es especialmente útil cuando querés revisar qué cambios realizaron otros desarrolladores antes de decidir si incorporarlos.

  1. Verificá el estado del proyecto: ejecutá git status para comprobar que no tengas cambios locales pendientes.
  2. Descargá la información del repositorio remoto: ejecutá git fetch. Git consultará el repositorio remoto y descargará los nuevos commits, ramas y referencias disponibles.
  3. Consultá qué cambios existen: podés utilizar git log --oneline main..origin/main para ver los commits que están en la rama remota y todavía no están en tu rama local.
  4. Compará los cambios: utilizá git diff main origin/main para comprobar exactamente qué diferencias existen entre tu rama local y la rama remota.
  5. Decidí qué hacer: después de revisar los cambios podés integrarlos utilizando git merge o actualizar tu rama mediante git pull.

Ejemplo básico:

git fetch

Después de ejecutar este comando, Git habrá actualizado la información que conoce sobre el repositorio remoto, pero no habrá modificado automáticamente tus archivos de trabajo.

Ejemplo de trabajo en equipo:

  1. Otro desarrollador realiza cambios en el proyecto y ejecuta git push.
  2. Vos ejecutás git fetch para consultar si existen novedades.
  3. Git descarga los nuevos commits y actualiza las referencias remotas.
  4. Podés consultar los cambios utilizando git log o git diff.
  5. Si los cambios son correctos y querés incorporarlos, podés utilizar git merge o git pull.

Una diferencia importante con git pull: git fetch descarga los cambios remotos pero no los integra automáticamente en tu rama actual. En cambio, git pull obtiene los cambios y posteriormente intenta integrarlos en tu rama.

Por ejemplo:

git fetch origin

Luego podés consultar las diferencias:

git diff main origin/main

Y si decidís incorporar esos cambios:

git merge origin/main

¿Cuándo conviene utilizar git fetch? Es especialmente útil cuando trabajás en equipo y querés mantener el control sobre cuándo incorporar cambios. Primero podés consultar qué ocurrió en GitHub, revisar los commits y diferencias, y recién después decidir si querés fusionarlos con tu trabajo.

Flujo habitual: git fetch → git log / git diff → revisar cambios → git merge.

Resumen: git fetch es una herramienta de consulta y sincronización de información remota. Te permite saber qué cambió en GitHub sin modificar inmediatamente tu trabajo local. Por eso resulta especialmente útil antes de realizar una integración de cambios.

BLOQUE 4 — Ramas y colaboración

Ramas en GitHub

Las ramas (branches) en GitHub permiten trabajar sobre diferentes versiones de un proyecto sin modificar directamente la rama principal. Son fundamentales para desarrollar nuevas funcionalidades, corregir errores y organizar el trabajo de varios desarrolladores de forma independiente.

  1. Consultar las ramas: desde GitHub podés acceder al selector de ramas del repositorio para ver las ramas disponibles y cambiar entre ellas.
  2. Crear una rama: desde GitHub podés crear una nueva rama a partir de una rama existente. Por ejemplo, nueva-funcionalidad puede crearse a partir de main.
  3. Trabajar en una rama: cada desarrollador puede realizar cambios en su propia rama sin modificar directamente main. Esto permite desarrollar funcionalidades de manera independiente.
  4. Crear una rama desde la terminal: también podés crearla localmente utilizando git switch -c nombre-rama.
  5. Subir la rama a GitHub: después de crearla localmente, podés enviarla al repositorio remoto mediante git push -u origin nombre-rama.
  6. Comparar ramas: GitHub permite comparar los cambios realizados entre dos ramas antes de integrarlos.
  7. Crear un Pull Request: cuando terminás el trabajo de una rama, podés crear un Pull Request para solicitar que tus cambios sean revisados antes de incorporarlos a otra rama, normalmente main.
  8. Fusionar la rama: después de revisar y aprobar los cambios, el Pull Request puede integrarse mediante un merge.
  9. Eliminar una rama: una vez incorporados los cambios, las ramas que ya no son necesarias pueden eliminarse del repositorio para mantenerlo organizado.

Ejemplo de trabajo: imaginá que el proyecto tiene una rama principal llamada main y necesitás desarrollar un sistema de inicio de sesión. Podés crear una rama llamada login, realizar allí todos los cambios y subirla a GitHub. Una vez terminado el trabajo, creás un Pull Request para que el equipo revise los cambios antes de fusionarlos con main.

Flujo habitual: main → crear rama → trabajar → commit → git push → Pull Request → revisión → merge → main.

Comandos relacionados:

  • git branch → muestra las ramas locales.
  • git branch -a → muestra las ramas locales y remotas conocidas.
  • git switch -c nombre-rama → crea una nueva rama y cambia a ella.
  • git switch nombre-rama → cambia a una rama existente.
  • git push -u origin nombre-rama → publica la rama local en GitHub.
  • git merge nombre-rama → integra una rama con la rama actual.
  • git branch -d nombre-rama → elimina una rama local que ya no necesitás.

Importante: una rama de GitHub y una rama local representan referencias del mismo sistema de control de versiones, pero pueden encontrarse en lugares diferentes. Por eso, después de crear una rama localmente, normalmente utilizamos git push para publicarla en GitHub.

Pull Requests

Los Pull Requests (PR) son una de las herramientas principales de GitHub para proponer, revisar e integrar cambios realizados en una rama. Permiten que otros colaboradores puedan analizar el código, realizar comentarios y aprobar los cambios antes de incorporarlos a otra rama, normalmente main.

  1. Trabajar en una rama: primero creás una rama independiente para desarrollar una funcionalidad, corregir un error o realizar cualquier otro cambio sin modificar directamente main.
  2. Realizar los cambios: trabajás normalmente en tu proyecto, modificando archivos, agregando funcionalidades o corrigiendo errores.
  3. Crear commits: una vez realizados los cambios, los guardás en el historial mediante git add y git commit.
  4. Subir la rama a GitHub: utilizás git push para publicar los commits de tu rama en el repositorio remoto.
  5. Crear el Pull Request: desde GitHub seleccionás la opción para crear un Pull Request y elegís la rama que contiene los cambios y la rama donde querés incorporarlos, por ejemplo login → main.
  6. Describir los cambios: el Pull Request permite explicar qué se modificó, por qué se realizaron esos cambios y qué aspectos debería revisar el equipo.
  7. Revisar el código: otros colaboradores pueden analizar los cambios realizados, comparar las diferencias entre las ramas y dejar comentarios o sugerencias.
  8. Realizar correcciones: si la revisión encuentra algún problema, podés modificar nuevamente tu rama y subir nuevos commits. Esos cambios aparecerán automáticamente dentro del mismo Pull Request.
  9. Aprobar los cambios: cuando la revisión está terminada y se cumplen las condiciones necesarias, los colaboradores autorizados pueden aprobar el Pull Request.
  10. Fusionar el Pull Request: finalmente, los cambios pueden incorporarse a la rama de destino mediante un merge.

Ejemplo práctico: imaginá que un proyecto tiene una rama principal llamada main y necesitás agregar un formulario de inicio de sesión. Creás una rama llamada login, desarrollás allí la funcionalidad y realizás varios commits. Después ejecutás git push -u origin login para subir la rama a GitHub.

Una vez publicada la rama, creás un Pull Request desde login hacia main. El resto del equipo puede revisar los archivos modificados, hacer comentarios y solicitar correcciones. Cuando los cambios están listos, el Pull Request puede aprobarse y fusionarse con main.

Flujo habitual: crear rama → trabajar → commit → git push → Pull Request → revisión → correcciones → aprobación → merge.

¿Qué permite hacer un Pull Request?

  • Proponer cambios antes de incorporarlos a otra rama.
  • Revisar el código realizado por otros colaboradores.
  • Comentar líneas específicas del código.
  • Solicitar modificaciones antes de aprobar los cambios.
  • Comprobar los cambios realizados entre dos ramas.
  • Ejecutar comprobaciones automáticas mediante herramientas configuradas en el repositorio.
  • Registrar quién revisó y aprobó los cambios.
  • Fusionar los cambios cuando cumplen las condiciones del proyecto.

Importante: un Pull Request no es un comando de Git. Es una funcionalidad de GitHub que utiliza las ramas y los commits de Git para facilitar la revisión y colaboración antes de integrar los cambios.

Comandos que normalmente intervienen:

  • git switch -c nombre-rama → crea una rama y cambia a ella.
  • git add . → prepara los cambios para el commit.
  • git commit -m "Descripción del cambio" → guarda los cambios en el historial.
  • git push -u origin nombre-rama → publica la rama y sus commits en GitHub.
  • git pull → actualiza el repositorio local con los cambios remotos.

Crear Pull Request

Crear un Pull Request en GitHub permite proponer que los cambios realizados en una rama sean revisados y posteriormente incorporados a otra rama. Es un paso habitual cuando trabajás en equipo, ya que permite revisar el código antes de modificar la rama principal.

  1. Crear una rama: comenzá trabajando en una rama independiente de main. Por ejemplo, podés crear una rama llamada login para desarrollar un sistema de inicio de sesión.
  2. Realizar los cambios: modificá, agregá o eliminá los archivos necesarios para completar la funcionalidad que estás desarrollando.
  3. Crear los commits: guardá los cambios en el historial de Git utilizando git add y git commit.
  4. Subir la rama a GitHub: publicá la rama y sus commits en el repositorio remoto con git push -u origin login.
  5. Abrir GitHub: ingresá al repositorio donde acabás de subir la rama. GitHub normalmente mostrará una opción para crear un Pull Request a partir de la nueva rama.
  6. Seleccionar las ramas: comprobá que la rama que contiene tus cambios sea la rama de origen y que la rama que recibirá los cambios sea la rama de destino. Por ejemplo: login → main.
  7. Agregar un título: escribí un título claro que permita entender rápidamente qué cambio propone el Pull Request.
  8. Describir los cambios: explicá qué se modificó, por qué se realizó el cambio y cualquier información que pueda ser útil para la persona encargada de revisar el código.
  9. Revisar los cambios: antes de crear el Pull Request, revisá los archivos y diferencias que GitHub muestra para asegurarte de que los cambios sean los esperados.
  10. Crear el Pull Request: finalmente, seleccioná la opción para crear el Pull Request. A partir de ese momento, los colaboradores podrán revisar los cambios y participar en la conversación.

Ejemplo: imaginá que estás trabajando en un sitio web y creaste la rama formulario-contacto. Después de terminar el formulario, realizás los commits correspondientes y ejecutás git push -u origin formulario-contacto.

En GitHub creás un Pull Request desde formulario-contacto hacia main. En la descripción podés explicar que agregaste el formulario de contacto, indicar qué archivos modificaste y cualquier aspecto que el equipo debería revisar.

Flujo completo: crear rama → modificar archivos → commit → git push → crear Pull Request → revisión → aprobación → merge.

¿Qué sucede después de crear el Pull Request?

  • Los colaboradores pueden revisar los cambios.
  • Se pueden agregar comentarios y sugerencias.
  • Podés realizar nuevos commits para corregir o mejorar el código.
  • GitHub actualiza automáticamente el Pull Request con esos nuevos commits.
  • Una vez finalizada la revisión, el Pull Request puede aprobarse y fusionarse.

Importante: crear un Pull Request no significa que los cambios ya estén incorporados en main. El Pull Request representa una propuesta de integración. La incorporación definitiva ocurre cuando el Pull Request se fusiona mediante un merge u otro método de integración disponible en el repositorio.

Merge de Pull Requests

El merge de un Pull Request es el proceso mediante el cual los cambios de una rama se incorporan a otra rama dentro de un repositorio de GitHub. Normalmente se utiliza para integrar el trabajo realizado en una rama de desarrollo con la rama principal, como main, después de que los cambios fueron revisados.

  1. Completar el trabajo: primero terminá los cambios en la rama donde estás desarrollando la funcionalidad o corrección.
  2. Crear los commits: guardá los cambios utilizando git add y git commit.
  3. Subir la rama: utilizá git push para enviar los commits a GitHub y permitir que estén disponibles para la revisión.
  4. Crear el Pull Request: proponé integrar tu rama con la rama de destino, por ejemplo login → main.
  5. Revisar los cambios: los colaboradores pueden analizar el código, realizar comentarios, solicitar modificaciones y comprobar que el Pull Request cumple con los requisitos del proyecto.
  6. Resolver los problemas: si existen correcciones pendientes o conflictos entre las ramas, deben solucionarse antes de completar la integración.
  7. Aprobar el Pull Request: cuando la revisión está terminada y se cumplen las condiciones establecidas por el repositorio, el Pull Request puede quedar listo para fusionarse.
  8. Realizar el merge: desde el Pull Request se selecciona la opción correspondiente para fusionar los cambios con la rama de destino.
  9. Confirmar la integración: GitHub incorpora los cambios a la rama de destino y el Pull Request queda marcado como integrado.

Ejemplo práctico: imaginá que un desarrollador creó la rama formulario-contacto a partir de main. Allí agregó un nuevo formulario, realizó sus commits y subió la rama a GitHub.

Después creó un Pull Request desde formulario-contacto hacia main. Otro miembro del equipo revisó los cambios y, una vez finalizada la revisión, el Pull Request se fusionó. Como resultado, el código del formulario pasó a formar parte de main.

¿Qué ocurre al hacer merge?

  • Los cambios de la rama de origen pasan a formar parte de la rama de destino.
  • El Pull Request queda registrado como integrado.
  • El historial de Git conserva la información de los commits involucrados.
  • La rama utilizada para desarrollar la funcionalidad puede conservarse o eliminarse, según las necesidades del proyecto.

Tipos de merge disponibles en GitHub:

  • Create a merge commit: integra los cambios creando un nuevo commit de merge que conecta las historias de ambas ramas.
  • Squash and merge: combina los commits del Pull Request en un único commit antes de incorporarlo a la rama de destino.
  • Rebase and merge: incorpora los commits del Pull Request sobre la historia de la rama de destino sin crear un commit de merge adicional.

Las opciones disponibles pueden depender de la configuración y las reglas establecidas en cada repositorio. Por eso, no todos los proyectos necesariamente permiten utilizar los tres métodos.

Después del merge: si la integración se realizó correctamente, quienes trabajan con una copia local del proyecto pueden actualizarla para obtener los cambios incorporados en GitHub mediante git pull.

Flujo completo: rama → cambios → commit → git push → Pull Request → revisión → aprobación → merge → git pull.

Importante: hacer merge no es simplemente «copiar archivos». Git integra los cambios dentro del historial del repositorio y puede detectar conflictos cuando las mismas partes de un archivo fueron modificadas de manera incompatible en diferentes ramas. Cuando esto ocurre, es necesario resolver el conflicto antes de completar la integración.

Resolver conflictos

Los conflictos en GitHub aparecen cuando Git no puede combinar automáticamente dos cambios realizados sobre la misma parte de un archivo. Suelen producirse al fusionar ramas mediante un Pull Request, especialmente cuando diferentes personas modificaron las mismas líneas de código.

  1. Identificar el conflicto: cuando GitHub detecta que no puede realizar la integración automáticamente, el Pull Request muestra que existen conflictos que deben resolverse.
  2. Consultar los archivos afectados: revisá qué archivos contienen conflictos y analizá qué cambios fueron realizados en cada rama.
  3. Decidir qué cambios conservar: compará las modificaciones y determiná si corresponde conservar los cambios de una rama, los de la otra o combinar manualmente ambas versiones.
  4. Resolver el conflicto: podés hacerlo directamente desde GitHub cuando el conflicto es compatible con las herramientas disponibles, o descargar la rama y resolverlo localmente con Git y un editor como VS Code.
  5. Eliminar las marcas del conflicto: cuando trabajás localmente, Git coloca marcas especiales dentro del archivo para indicar las versiones en conflicto. Debés editar el archivo y dejar únicamente el código correcto.
  6. Comprobar el resultado: revisá el archivo después de resolver el conflicto y, si es posible, ejecutá las pruebas del proyecto para verificar que los cambios sigan funcionando correctamente.
  7. Preparar la resolución: utilizá git add sobre los archivos que ya fueron corregidos.
  8. Crear el commit: guardá la resolución mediante git commit. Git registrará que el conflicto fue solucionado.
  9. Subir los cambios: ejecutá git push para enviar la resolución a GitHub. El Pull Request se actualizará automáticamente.
  10. Completar el merge: cuando todos los conflictos estén resueltos y las comprobaciones necesarias sean correctas, el Pull Request podrá fusionarse.

Ejemplo práctico: imaginá que dos desarrolladores trabajan sobre el mismo archivo index.html. El desarrollador A modifica una línea para agregar un título y el desarrollador B modifica esa misma línea para agregar otro contenido.

Cuando se intenta fusionar una rama con la otra, Git detecta que existen dos versiones diferentes de la misma parte del archivo y no puede determinar automáticamente cuál debe conservarse. En ese momento se produce un conflicto.

Cuando el conflicto se resuelve localmente, Git puede mostrar marcas como estas:

<<<<<<< HEAD
<h1>Título del proyecto</h1>
=======
<h1>Mi proyecto web</h1>
>>>>>>> otra-rama

Estas marcas indican las dos versiones que entraron en conflicto. Debés decidir qué código conservar y eliminar las marcas <<<<<<<, ======= y >>>>>>>.

Comandos útiles para resolver conflictos:

  • git status → muestra los archivos que tienen conflictos.
  • git diff → permite revisar las diferencias.
  • git add archivo → indica a Git que el conflicto de ese archivo fue resuelto.
  • git commit → registra la resolución del conflicto.
  • git push → sube la resolución a GitHub.
  • git merge --abort → cancela un merge en curso y devuelve el estado anterior al inicio del merge.

¿Cómo evitar conflictos?

  • Trabajá en ramas independientes para cada funcionalidad o corrección.
  • Actualizá tu rama con frecuencia antes de comenzar nuevos cambios.
  • Realizá commits pequeños y relacionados con un único objetivo.
  • Comunicá al equipo cuando estés modificando una parte importante del proyecto.
  • Revisá los Pull Requests antes de fusionarlos.

Importante: un conflicto no significa que el proyecto esté dañado. Significa que Git necesita que una persona decida cómo combinar cambios que no puede integrar automáticamente. La resolución correcta depende del objetivo del proyecto y del código que debe conservarse.

Flujo habitual: Pull Request → detectar conflicto → revisar cambios → resolver → git add → git commit → git push → comprobar → merge.

Colaboradores

Los colaboradores en GitHub son personas a las que se les concede acceso a un repositorio para que puedan participar directamente en su desarrollo. Esto permite que varias personas trabajen sobre un mismo proyecto, creen ramas, realicen commits, abran Pull Requests y, según sus permisos, administren diferentes aspectos del repositorio.

  1. Acceder al repositorio: ingresá al repositorio de GitHub en el que querés agregar una persona como colaborador.
  2. Abrir la configuración: seleccioná la sección Settings del repositorio para acceder a sus opciones de configuración.
  3. Buscar las opciones de acceso: dentro de la configuración, accedé a la sección relacionada con el acceso y la administración de colaboradores.
  4. Agregar una persona: utilizá la opción para agregar o invitar a un colaborador e indicá su nombre de usuario o la información solicitada por GitHub.
  5. Enviar la invitación: seleccioná el nivel de acceso correspondiente y enviá la invitación. La persona deberá aceptarla para comenzar a colaborar en el repositorio.
  6. Trabajar en el proyecto: una vez que tiene acceso, el colaborador puede clonar el repositorio, crear ramas, realizar cambios, hacer commits y subirlos a GitHub según los permisos que tenga.
  7. Utilizar Pull Requests: en un equipo es habitual que los colaboradores trabajen mediante ramas y Pull Requests para revisar los cambios antes de incorporarlos a la rama principal.
  8. Administrar los permisos: los permisos pueden modificarse posteriormente si las necesidades del proyecto cambian. También es posible retirar el acceso de una persona cuando ya no debe colaborar en el repositorio.

Ejemplo práctico: imaginá que estás desarrollando una página web y tenés un repositorio llamado mi-sitio-web. Podés agregar a otro desarrollador como colaborador para que trabaje junto con vos en el proyecto.

El colaborador puede clonar el repositorio, crear una rama llamada contacto, desarrollar el formulario de contacto y subir los cambios a GitHub. Después puede crear un Pull Request para que revises el código antes de incorporarlo a main.

¿Qué puede hacer un colaborador?

  • Acceder al repositorio según el permiso asignado.
  • Clonar el proyecto y trabajar con una copia local.
  • Crear y utilizar ramas.
  • Realizar commits.
  • Subir cambios mediante git push, cuando sus permisos lo permiten.
  • Crear y participar en Pull Requests.
  • Revisar cambios y realizar comentarios.
  • Participar en Issues y otras herramientas del repositorio según sus permisos.

Permisos y acceso: no todos los colaboradores necesariamente tienen las mismas capacidades. GitHub permite utilizar diferentes niveles de permisos para determinar qué acciones puede realizar cada persona dentro de un repositorio.

Por ejemplo, una persona puede tener permisos suficientes para trabajar con el código, mientras que otra puede contar además con permisos administrativos para modificar determinadas configuraciones del repositorio.

Colaboradores y ramas: agregar personas al repositorio no significa que todos deban trabajar directamente sobre main. En un flujo organizado, cada colaborador suele trabajar en una rama independiente y utilizar Pull Requests para proponer la integración de sus cambios.

Flujo habitual de un equipo: agregar colaborador → clonar repositorio → crear rama → realizar cambios → commit → push → Pull Request → revisión → merge.

Importante: los colaboradores son diferentes de los usuarios que simplemente pueden consultar un repositorio público. Un repositorio público puede ser visible para muchas personas, pero eso no significa que todas ellas tengan permisos para modificar directamente su contenido.

BLOQUE 5 — Gestión de proyectos

Issues

Los GitHub Issues permiten registrar y organizar tareas, errores, mejoras, preguntas y otras actividades relacionadas con un proyecto. Funcionan como un sistema de seguimiento que ayuda al equipo a saber qué debe hacerse, quién está trabajando en cada tarea y qué problemas todavía están pendientes.

  1. Acceder a Issues: dentro de un repositorio de GitHub, ingresá a la sección Issues para consultar las tareas y problemas registrados en el proyecto.
  2. Crear un Issue: seleccioná la opción para crear un nuevo Issue y escribí un título que describa claramente el problema, tarea o propuesta.
  3. Describir el problema o tarea: utilizá el cuerpo del Issue para explicar qué sucede, qué se necesita realizar, cómo reproducir un error o cualquier otra información relevante.
  4. Agregar etiquetas: podés utilizar Labels para clasificar el Issue. Por ejemplo, bug, feature, documentation o help wanted.
  5. Asignar responsables: podés asignar el Issue a uno o varios colaboradores para indicar quiénes se encargarán de trabajar en él.
  6. Relacionar el Issue con el trabajo: un Issue puede utilizarse como referencia durante el desarrollo de una funcionalidad y relacionarse con Pull Requests y otros elementos del proyecto.
  7. Comentar y actualizar: los colaboradores pueden agregar comentarios para compartir información, hacer preguntas, indicar avances o proponer soluciones.
  8. Realizar el trabajo: cuando un desarrollador comienza a solucionar el problema o desarrollar la tarea, puede crear una rama específica y trabajar sobre ella.
  9. Cerrar el Issue: cuando el problema fue solucionado o la tarea fue completada, el Issue puede cerrarse para indicar que ya no está pendiente.

Ejemplo práctico: imaginá que los usuarios de una página web informan que el botón Enviar de un formulario no funciona. Podés crear un Issue llamado “El botón de contacto no envía el formulario” y explicar qué ocurre y cómo reproducir el problema.

Después podés asignar el Issue a un colaborador y agregar la etiqueta bug. El desarrollador crea una rama llamada corregir-formulario, soluciona el problema, realiza los commits y abre un Pull Request.

Una vez revisado y fusionado el Pull Request, el Issue puede cerrarse porque el problema registrado ya fue solucionado.

¿Para qué se utilizan los Issues?

  • Registrar errores o problemas del proyecto.
  • Planificar nuevas funcionalidades.
  • Organizar tareas pendientes.
  • Proponer mejoras.
  • Hacer preguntas relacionadas con el proyecto.
  • Asignar tareas a colaboradores.
  • Clasificar actividades mediante etiquetas.
  • Seguir el progreso de diferentes trabajos.
  • Relacionar tareas con Pull Requests y cambios de código.

Issue y Pull Request no son lo mismo: un Issue sirve principalmente para registrar y organizar una tarea, problema, pregunta o propuesta. Un Pull Request, en cambio, se utiliza para proponer cambios de código que pueden ser revisados y posteriormente integrados en otra rama.

Ejemplo de flujo: Issue → asignar tarea → crear rama → realizar cambios → commit → push → Pull Request → revisión → merge → cerrar Issue.

Importante: los Issues no están limitados exclusivamente a errores de programación. También pueden utilizarse para organizar tareas, documentar necesidades, planificar funcionalidades y mantener una lista de trabajo pendiente dentro del proyecto.

Labels y Milestones

Las Labels y los Milestones son herramientas de GitHub que ayudan a organizar y seguir el trabajo de un proyecto. Las Labels permiten clasificar Issues y Pull Requests mediante etiquetas, mientras que los Milestones permiten agrupar varios Issues y Pull Requests relacionados con un objetivo o una etapa determinada del proyecto.

  1. Utilizar Labels: las etiquetas permiten identificar rápidamente el tipo o estado de un Issue o Pull Request. Por ejemplo, podés crear etiquetas como bug, feature, documentation o urgent.
  2. Crear una Label: desde la sección de Issues del repositorio podés acceder a las etiquetas y crear una nueva indicando su nombre, descripción y, cuando corresponda, un color.
  3. Asignar una Label: al crear o editar un Issue o Pull Request podés agregar una o varias etiquetas para clasificarlo.
  4. Utilizar varias Labels: un mismo Issue puede tener diferentes etiquetas. Por ejemplo, podría utilizar bug para indicar el tipo de problema y alta-prioridad para indicar que requiere atención.
  5. Crear un Milestone: un Milestone representa un objetivo o etapa del proyecto. Por ejemplo, podés crear uno llamado Versión 1.0 para agrupar todas las tareas necesarias antes de publicar esa versión.
  6. Asignar Issues a un Milestone: una vez creado el Milestone, podés asociarle los Issues relacionados con ese objetivo.
  7. Seguir el progreso: GitHub permite consultar cuántos elementos asociados a un Milestone fueron completados y cuáles todavía están pendientes.
  8. Utilizar Milestones para organizar etapas: podés crear diferentes Milestones para representar versiones, entregas o etapas del desarrollo del proyecto.

Ejemplo práctico con Labels: imaginá que estás desarrollando una página web y tenés varios Issues pendientes. Podés utilizar bug para los errores, feature para las nuevas funcionalidades y documentation para las tareas relacionadas con la documentación.

De esta manera, cuando consultás los Issues del repositorio, podés identificar rápidamente qué tipo de trabajo representa cada uno y utilizar los filtros de GitHub para encontrar los elementos que necesitás.

Ejemplo práctico con Milestones: supongamos que estás preparando la versión 1.0 de una aplicación. Podés crear un Milestone llamado Versión 1.0 y asociar todos los Issues necesarios para completar esa versión.

Por ejemplo, podrías incluir tareas como corregir errores, crear el formulario de registro, mejorar el diseño y preparar la documentación. A medida que cada tarea se completa, el progreso del Milestone permite visualizar cuánto trabajo queda pendiente.

Diferencia entre Labels y Milestones:

  • Labels: sirven principalmente para clasificar y filtrar Issues y Pull Requests.
  • Milestones: sirven para agrupar trabajo relacionado con un objetivo o etapa del proyecto y realizar un seguimiento de su progreso.
  • Una Label puede utilizarse en muchos Issues y Pull Requests independientemente de una etapa concreta.
  • Un Milestone reúne diferentes Issues y Pull Requests que forman parte de un mismo objetivo.

Ejemplo de organización:

  • Milestone: Versión 1.0
  • Issue: Crear formulario de registro → feature
  • Issue: Corregir error del login → bug + alta-prioridad
  • Issue: Crear documentación → documentation

En este ejemplo, las Labels indican qué tipo de trabajo representa cada tarea, mientras que el Milestone indica que todas esas tareas forman parte de un mismo objetivo: preparar la versión 1.0.

Flujo habitual: crear Issue → asignar Labels → asociar a Milestone → trabajar → Pull Request → completar → cerrar Issue.

Importante: Labels y Milestones cumplen funciones diferentes y pueden utilizarse conjuntamente. Las etiquetas ayudan a clasificar el trabajo, mientras que los Milestones permiten organizarlo alrededor de objetivos concretos y realizar un seguimiento del progreso.

GitHub Projects

GitHub Projects es una herramienta de GitHub que permite organizar, planificar y realizar un seguimiento visual del trabajo de un proyecto. Puede utilizarse para gestionar tareas, Issues y Pull Requests desde diferentes tipos de vistas, facilitando la planificación tanto de proyectos personales como de equipos de desarrollo.

  1. Crear un Project: desde GitHub podés crear un nuevo proyecto y asignarle un nombre que permita identificar fácilmente su objetivo, por ejemplo Desarrollo de mi sitio web.
  2. Elegir una vista: GitHub Projects permite organizar la información mediante diferentes vistas, como una tabla, un tablero o una hoja de ruta, según la forma en que quieras visualizar el trabajo.
  3. Agregar elementos: podés incorporar Issues, Pull Requests y otros elementos relacionados con el trabajo que necesitás organizar.
  4. Crear tareas: también podés utilizar el Project para organizar tareas que todavía no necesitan estar representadas como un Issue del repositorio.
  5. Organizar el trabajo: los elementos pueden clasificarse mediante campos, estados, etiquetas y diferentes propiedades para facilitar su seguimiento.
  6. Utilizar estados: podés organizar las tareas según su situación, por ejemplo Todo, In Progress y Done.
  7. Asignar responsables: cuando trabajás en equipo, podés indicar quién se encargará de una determinada tarea.
  8. Establecer fechas: los elementos pueden organizarse utilizando fechas para planificar cuándo deberían comenzar o finalizar determinadas tareas.
  9. Filtrar y agrupar: GitHub Projects permite utilizar diferentes opciones para mostrar únicamente la información que necesitás analizar en cada momento.
  10. Seguir el progreso: a medida que las tareas avanzan, podés actualizar su estado y utilizar las diferentes vistas para conocer qué trabajo está pendiente, en desarrollo o terminado.

Ejemplo práctico: imaginá que estás desarrollando un sitio web. Podés crear un GitHub Project llamado Nuevo sitio web y agregar tareas como Diseñar la página de inicio, Crear el formulario de contacto, Adaptar el diseño para móviles y Publicar el sitio.

Después podés organizar esas tareas en un tablero con columnas como Por hacer, En progreso y Completado. A medida que trabajás, cada tarea puede cambiar de columna para reflejar su estado actual.

GitHub Projects y los Issues: ambas herramientas pueden trabajar conjuntamente. Un Issue puede representar una tarea o problema concreto, mientras que GitHub Projects permite organizar visualmente ese Issue junto con otras tareas y Pull Requests.

¿Qué permite hacer GitHub Projects?

  • Planificar el trabajo de un proyecto.
  • Organizar tareas y actividades pendientes.
  • Visualizar el progreso del desarrollo.
  • Gestionar Issues y Pull Requests.
  • Asignar responsables.
  • Establecer fechas y prioridades.
  • Crear diferentes vistas para organizar la información.
  • Filtrar y agrupar tareas según diferentes criterios.
  • Coordinar el trabajo de un equipo.

Ejemplo de flujo: crear Project → agregar tareas → organizar → asignar responsables → trabajar → actualizar estados → completar.

Importante: GitHub Projects no reemplaza a Git, los repositorios, las ramas, los Issues ni los Pull Requests. Su función es ayudar a organizar y visualizar el trabajo que se realiza utilizando esas herramientas.

BLOQUE 6 — Open Source

Fork

Un Fork en GitHub es una copia de un repositorio que se crea dentro de otra cuenta de GitHub. Permite trabajar sobre un proyecto sin modificar directamente el repositorio original. Es especialmente útil cuando querés contribuir a proyectos en los que no tenés permisos de escritura.

  1. Elegir el repositorio: ingresá al repositorio de GitHub que querés copiar. Puede tratarse de un proyecto de código abierto al que quieras aportar una mejora.
  2. Crear el Fork: desde el repositorio original utilizá la opción Fork. GitHub creará una copia del repositorio dentro de tu propia cuenta.
  3. Seleccionar el propietario: si GitHub te lo solicita, elegí la cuenta u organización donde querés crear el Fork.
  4. Trabajar sobre tu Fork: una vez creado, tendrás tu propia copia del repositorio. Podés modificar archivos, crear ramas y realizar commits sin modificar directamente el proyecto original.
  5. Clonar el Fork: si querés trabajar desde tu computadora, podés clonar tu Fork utilizando git clone.
  6. Crear una rama: para organizar los cambios, normalmente se crea una rama independiente desde tu Fork, por ejemplo mejora-documentacion.
  7. Realizar los cambios: modificá el proyecto, agregá los archivos necesarios y guardá los cambios mediante commits.
  8. Subir los cambios: utilizá git push para enviar tu rama a tu Fork en GitHub.
  9. Crear un Pull Request: si querés proponer tus cambios al proyecto original, podés crear un Pull Request desde tu Fork hacia el repositorio original.
  10. Esperar la revisión: los responsables del proyecto original pueden revisar tu propuesta, solicitar cambios, aprobarla y finalmente incorporarla al proyecto.

Ejemplo práctico: imaginá que encontrás un proyecto de código abierto llamado mi-proyecto. No tenés permisos para modificar directamente su repositorio, pero querés corregir un error en la documentación.

Primero creás un Fork del repositorio. GitHub genera una copia dentro de tu cuenta. Después clonás esa copia en tu computadora, creás una rama llamada corregir-documentacion, realizás los cambios y los subís a tu Fork.

Finalmente, creás un Pull Request desde tu Fork hacia el repositorio original. Los responsables del proyecto pueden revisar tus cambios y decidir si los incorporan.

Fork y clonación no son lo mismo:

  • Fork: crea una copia del repositorio dentro de GitHub, asociada a tu cuenta.
  • Clone: descarga un repositorio de GitHub a tu computadora para trabajar localmente.
  • Fork + Clone: es un flujo habitual para contribuir a proyectos en los que no tenés permisos de escritura.

Fork y Pull Request también cumplen funciones diferentes: el Fork crea tu propia copia del repositorio, mientras que el Pull Request permite proponer que los cambios realizados en tu copia o en una rama sean incorporados al repositorio de destino.

Flujo habitual para contribuir a un proyecto: Fork → Clone → crear rama → realizar cambios → commit → push → Pull Request → revisión → merge.

¿Para qué se utiliza un Fork?

  • Contribuir a proyectos de código abierto.
  • Trabajar sobre un proyecto sin modificar directamente el repositorio original.
  • Experimentar con cambios de manera independiente.
  • Preparar mejoras para posteriormente proponerlas mediante un Pull Request.
  • Mantener una copia del proyecto dentro de tu propia cuenta de GitHub.

Importante: un Fork no significa simplemente descargar los archivos del proyecto. GitHub mantiene una relación entre el Fork y el repositorio original, lo que facilita trabajar de forma independiente y posteriormente proponer cambios mediante un Pull Request.

Fork + Pull Request

El flujo Fork + Pull Request es una forma habitual de contribuir a proyectos de GitHub cuando no tenés permisos para modificar directamente el repositorio original. Primero creás un Fork para obtener una copia del proyecto en tu cuenta y después utilizás un Pull Request para proponer que tus cambios sean incorporados al repositorio original.

  1. Elegir el repositorio: buscá el proyecto de GitHub al que querés contribuir. Por ejemplo, puede ser un proyecto de código abierto en el que encontraste un error o querés agregar una mejora.
  2. Crear el Fork: seleccioná la opción Fork para crear una copia del repositorio dentro de tu propia cuenta de GitHub.
  3. Clonar tu Fork: descargá tu copia a la computadora utilizando git clone para poder trabajar con los archivos localmente.
  4. Ingresar al proyecto: utilizá cd nombre-del-repositorio para acceder a la carpeta que contiene el proyecto.
  5. Crear una rama: creá una rama independiente para realizar tu contribución. Por ejemplo, corregir-error.
  6. Realizar los cambios: modificá los archivos necesarios y comprobá que la solución funcione correctamente.
  7. Crear los commits: utilizá git add y git commit para guardar los cambios en el historial de Git.
  8. Subir la rama: ejecutá git push -u origin corregir-error para publicar tu rama en tu Fork de GitHub.
  9. Crear el Pull Request: desde GitHub proponé integrar los cambios de tu rama con el repositorio original. Por ejemplo, tu rama corregir-error puede dirigirse hacia la rama main del repositorio original.
  10. Describir la contribución: agregá un título y una descripción explicando qué problema solucionaste, qué cambios realizaste y cualquier información relevante para los responsables del proyecto.
  11. Esperar la revisión: los responsables del repositorio original pueden revisar tu código, realizar comentarios y solicitar modificaciones.
  12. Realizar correcciones: si te solicitan cambios, podés modificar nuevamente tu rama y realizar nuevos commits. Después utilizás git push para actualizar automáticamente el Pull Request.
  13. Esperar la integración: si la propuesta es aprobada, los responsables del proyecto pueden fusionar el Pull Request con el repositorio original.

Ejemplo práctico: imaginá que encontrás un error en un proyecto de código abierto. No tenés permisos para modificar directamente el repositorio del propietario, pero querés solucionarlo.

Primero creás un Fork del proyecto. Después clonás esa copia en tu computadora y creás una rama llamada corregir-error-login. Realizás la corrección, creás un commit y subís la rama a tu Fork.

Finalmente, creás un Pull Request desde tu Fork hacia el repositorio original. El equipo responsable puede revisar la solución y, si considera que los cambios son adecuados, incorporarlos al proyecto.

¿Qué función cumple cada elemento?

  • Fork: crea una copia del repositorio dentro de tu cuenta de GitHub.
  • Clone: descarga esa copia en tu computadora para trabajar localmente.
  • Branch: permite realizar los cambios de manera independiente.
  • Commit: registra los cambios realizados.
  • Push: sube tus commits a tu Fork.
  • Pull Request: propone incorporar tus cambios al repositorio de destino.
  • Merge: integra los cambios cuando el Pull Request es aceptado.

Flujo completo:

Fork → Clone → Branch → cambios → Commit → Push → Pull Request → revisión → correcciones → Merge

Fork + Pull Request vs. colaboración directa: cuando sos colaborador de un repositorio y tenés permisos suficientes, normalmente podés crear una rama directamente dentro del repositorio original y abrir un Pull Request desde allí. En cambio, cuando no tenés permisos de escritura, el Fork te proporciona una copia propia desde la que podés realizar tu trabajo y proponerlo mediante un Pull Request.

Importante: crear un Fork no modifica el repositorio original. Los cambios realizados en tu Fork permanecen separados hasta que se propone un Pull Request y los responsables del proyecto deciden si quieren incorporarlos.

Open Source

Open Source, o código abierto, hace referencia al software cuyo código fuente está disponible para que otras personas puedan estudiarlo, utilizarlo, modificarlo y, según las condiciones establecidas por su licencia, redistribuirlo. GitHub es una de las plataformas más utilizadas para alojar y colaborar en este tipo de proyectos.

  1. Encontrar un proyecto: en GitHub podés buscar proyectos de código abierto relacionados con diferentes lenguajes, tecnologías y áreas de programación.
  2. Consultar el repositorio: antes de realizar cambios, revisá el código, el README.md, la documentación y las instrucciones proporcionadas por los responsables del proyecto.
  3. Leer la licencia: comprobá qué licencia utiliza el proyecto, ya que establece las condiciones bajo las cuales se puede utilizar, modificar y distribuir el software.
  4. Revisar las contribuciones: muchos proyectos tienen un archivo como CONTRIBUTING.md donde explican cómo deben realizarse las contribuciones y qué normas debe seguir la comunidad.
  5. Crear un Fork: si no tenés permisos para escribir directamente en el repositorio, podés crear un Fork para disponer de una copia del proyecto dentro de tu cuenta.
  6. Crear una rama: desde tu Fork podés crear una rama independiente para desarrollar una funcionalidad, corregir un error o mejorar la documentación.
  7. Realizar los cambios: trabajá sobre el proyecto, probá las modificaciones y asegurate de respetar las reglas establecidas por sus responsables.
  8. Crear commits: guardá los cambios utilizando commits claros que permitan comprender qué modificaste.
  9. Subir los cambios: utilizá git push para publicar tu rama en tu Fork de GitHub.
  10. Crear un Pull Request: si querés proponer tus cambios al proyecto original, abrí un Pull Request explicando qué modificaste y por qué.
  11. Participar en la revisión: los responsables y otros colaboradores pueden revisar tu propuesta, realizar comentarios y solicitar modificaciones antes de aceptarla.

Ejemplo práctico: imaginá que encontrás un error en la documentación de una biblioteca de JavaScript que utilizás. Podés crear un Fork del proyecto, modificar la documentación, crear un commit y subir los cambios a tu repositorio.

Después podés abrir un Pull Request hacia el proyecto original. Los responsables revisarán tu propuesta y, si deciden incorporarla, realizarán el merge de los cambios.

¿Qué características tiene un proyecto Open Source?

  • Su código fuente puede estar disponible públicamente.
  • Puede recibir contribuciones de diferentes desarrolladores.
  • Utiliza una licencia que establece las condiciones de uso y distribución.
  • Puede desarrollarse de manera colaborativa.
  • Puede utilizar Issues para organizar problemas y tareas.
  • Puede utilizar Pull Requests para revisar contribuciones.
  • Puede contar con documentación y normas para los colaboradores.

Open Source no significa simplemente «código gratis»: que un proyecto permita acceder a su código fuente no significa que no tenga condiciones. La licencia determina qué se puede hacer con ese código y qué obligaciones deben respetarse.

GitHub y Open Source: GitHub proporciona herramientas que facilitan el desarrollo colaborativo, como repositorios públicos, Issues, Pull Requests, Forks, revisiones de código y discusiones. Estas funcionalidades permiten que personas de diferentes lugares puedan participar en un mismo proyecto.

Ejemplo de flujo para contribuir: buscar proyecto → leer documentación y licencia → Fork → Clone → crear rama → cambios → Commit → Push → Pull Request → revisión → Merge.

Importante: no todos los proyectos alojados públicamente en GitHub tienen necesariamente las mismas condiciones de uso o contribución. Antes de reutilizar código o realizar una contribución, es recomendable consultar la licencia, la documentación y las reglas específicas del proyecto.

BLOQUE 7 — Perfil y publicación

GitHub Profile

El GitHub Profile es la página pública asociada a tu cuenta de GitHub donde podés presentar información sobre vos, tus proyectos y tu actividad dentro de la plataforma. Puede funcionar como una presentación de tu trabajo y, especialmente para desarrolladores, como una forma de mostrar proyectos y contribuciones.

  1. Acceder a tu perfil: ingresá a GitHub con tu cuenta y seleccioná tu imagen de perfil para acceder a tu página personal.
  2. Configurar la información básica: desde las opciones de perfil podés agregar o modificar información como tu nombre, biografía, ubicación, sitio web y otros datos que quieras mostrar públicamente.
  3. Agregar una fotografía: podés utilizar una imagen de perfil que permita identificar visualmente tu cuenta.
  4. Agregar una biografía: utilizá la sección de biografía para explicar brevemente quién sos, qué tecnologías utilizás o en qué tipo de proyectos trabajás.
  5. Agregar tu sitio web: si tenés una página personal, portfolio o sitio profesional, podés incluirlo en tu perfil para que otras personas puedan acceder a él.

  7. Presentar tus proyectos: podés destacar determinados repositorios para facilitar que otras personas encuentren los proyectos que considerás más importantes.
  8. Mostrar tu actividad: tu perfil puede mostrar información relacionada con tus contribuciones y actividad pública en GitHub.
  9. Revisar la información pública: antes de completar tu perfil, comprobá qué información querés mostrar públicamente y evitá incluir datos personales que no sean necesarios.

Ejemplo práctico: imaginá que estás aprendiendo desarrollo web y querés utilizar GitHub como portfolio. Podés configurar tu perfil con una breve descripción, agregar tu sitio web y destacar repositorios donde hayas desarrollado proyectos utilizando HTML, CSS y JavaScript.

También podés crear un Profile README para presentar tus conocimientos, tecnologías, proyectos destacados y enlaces relevantes. De esta manera, cuando otra persona visite tu perfil, puede obtener rápidamente una visión general de tu trabajo.

¿Qué podés mostrar en tu GitHub Profile?

  • Nombre y fotografía de perfil.

Por ejemplo, si tu nombre de usuario fuera juan123, el repositorio especial sería juan123/juan123. Dentro de ese repositorio podés crear un archivo README.md con información que quieras presentar en tu perfil.

Importante: un perfil de GitHub no es lo mismo que la configuración general de la cuenta. GitHub Pages

GitHub Pages es un servicio de GitHub que permite publicar sitios web directamente desde un repositorio. Es especialmente útil para páginas estáticas creadas con HTML, CSS y JavaScript, ya que permite convertir un repositorio en un sitio web accesible desde Internet sin necesidad de contratar un servidor web tradicional.

  1. Crear un repositorio: primero necesitás un repositorio de GitHub donde estarán los archivos de tu sitio web. Por ejemplo, podés crear uno llamado mi-sitio-web.
  2. Agregar los archivos: incorporá al repositorio los archivos necesarios para tu página, como index.html, archivos CSS, JavaScript e imágenes.
  3. Subir los cambios: si trabajás desde tu computadora, podés utilizar Git para realizar commits y enviar los archivos a GitHub mediante git push.
  4. Acceder a Pages: dentro del repositorio ingresá a Settings y buscá la sección relacionada con Pages.
  5. Elegir la fuente de publicación: seleccioná la rama y la carpeta desde las que GitHub Pages debe obtener los archivos del sitio.
  6. Guardar la configuración: confirmá la configuración de publicación para que GitHub pueda generar y publicar el sitio.
  7. Esperar la publicación: después de que GitHub procese el repositorio, el sitio quedará disponible mediante una dirección web proporcionada por GitHub Pages.
  8. Actualizar el sitio: cuando realices nuevos cambios en los archivos y los subas al repositorio, GitHub Pages puede volver a publicar el sitio utilizando la configuración establecida.

Ejemplo práctico: imaginá que desarrollaste una página personal utilizando index.html, style.css y script.js. Subís esos archivos a un repositorio de GitHub y configurás GitHub Pages para publicar el contenido.

Una vez realizada la publicación, otras personas pueden acceder a la página mediante la dirección web generada por GitHub Pages. Si posteriormente modificás el código y hacés un nuevo git push, el sitio puede actualizarse con esos cambios.

¿Para qué se utiliza GitHub Pages?

  • Publicar sitios web estáticos.
  • Crear portfolios personales.
  • Publicar documentación de proyectos.
  • Crear páginas para proyectos de código abierto.
  • Mostrar proyectos desarrollados con HTML, CSS y JavaScript.
  • Publicar blogs y páginas informativas compatibles con el servicio.

¿Qué tipo de sitios se pueden publicar?

GitHub Pages es especialmente apropiado para sitios que pueden ejecutarse en el navegador sin depender de un servidor propio para procesar código del lado del servidor. Por ejemplo, una página creada con HTML, CSS y JavaScript puede publicarse directamente.

En cambio, una aplicación que necesite ejecutar código del lado del servidor, como PHP o un backend de Node.js, no puede utilizar GitHub Pages como si fuera un servidor tradicional para ejecutar ese código.

GitHub Pages y Git: Git se encarga de controlar las versiones de los archivos y GitHub almacena el repositorio de forma remota. GitHub Pages utiliza esos archivos almacenados en el repositorio como fuente para publicar el sitio web.

Flujo habitual: crear sitio → crear repositorio → subir archivos → configurar GitHub Pages → publicar → realizar cambios → git push → actualizar sitio.

Importante: GitHub Pages está pensado principalmente para la publicación de sitios estáticos. Si tu proyecto necesita un servidor que procese solicitudes, ejecute código del backend o utilice una base de datos directamente, normalmente necesitarás un servicio de hosting que proporcione esas capacidades.

Publicar una web con GitHub Pages

Una vez que conocemos qué es GitHub Pages, podemos utilizarlo para llevar un proyecto web desde nuestra computadora hasta una dirección accesible desde Internet. Para una página creada con HTML, CSS y JavaScript, el proceso consiste en subir los archivos a un repositorio de GitHub y configurar GitHub Pages para utilizar ese repositorio como fuente de publicación.

  1. Preparar el proyecto: asegurate de tener los archivos necesarios para tu sitio, por ejemplo index.html, style.css y script.js.
  2. Comprobar el archivo principal: el archivo index.html debe encontrarse en la ubicación que utilizará GitHub Pages como fuente del sitio. Este archivo normalmente funciona como la página principal.
  3. Crear un repositorio en GitHub: iniciá sesión en GitHub y creá un repositorio para almacenar los archivos de tu proyecto. Por ejemplo, podés llamarlo mi-sitio-web.
  4. Subir los archivos: podés cargar los archivos directamente desde la interfaz de GitHub o utilizar Git desde tu computadora. Si trabajás localmente, el flujo habitual es git add, git commit y git push.
  5. Abrir la configuración del repositorio: dentro del repositorio ingresá en Settings y buscá la sección Pages.
  6. Seleccionar la fuente de publicación: en la configuración de GitHub Pages elegí la rama que contiene los archivos del sitio, por ejemplo main, y seleccioná la carpeta que corresponde a tu proyecto.
  7. Guardar la configuración: confirmá la configuración para que GitHub Pages pueda comenzar el proceso de publicación.
  8. Esperar la publicación: GitHub procesará el repositorio y, cuando el sitio esté publicado, mostrará la dirección desde la que podés acceder a la página.
  9. Abrir la web: utilizá la dirección proporcionada por GitHub Pages para comprobar que el sitio funciona correctamente.
  10. Actualizar la página: cuando modifiques el proyecto, subí nuevamente los cambios al repositorio. GitHub Pages utilizará la nueva versión para actualizar el sitio publicado.

Ejemplo práctico: imaginá que tenés esta estructura en tu computadora:

mi-sitio-web/
├── index.html
├── style.css
├── script.js
└── imagenes/
    └── logo.png

Primero subís estos archivos a un repositorio de GitHub. Después configurás GitHub Pages para utilizar la rama main y la carpeta correspondiente como fuente de publicación.

Una vez publicado el proyecto, GitHub Pages genera una dirección web desde la que cualquier persona puede acceder al sitio. Si posteriormente modificás index.html, style.css o script.js, realizás un nuevo commit y ejecutás git push, los cambios podrán reflejarse en la página publicada.

Si trabajás desde la terminal:

# Inicializar Git en el proyecto
git init

# Agregar los archivos
git add .

# Crear el primer commit
git commit -m "Publicar sitio web"

# Conectar el proyecto con GitHub
git remote add origin URL_DEL_REPOSITORIO

# Subir los archivos a GitHub
git push -u origin main

Después de subir el proyecto, la configuración de GitHub Pages se realiza desde las opciones del repositorio. A partir de ese momento, GitHub Pages utiliza los archivos seleccionados como fuente para publicar el sitio.

¿Qué ocurre cuando modificás la web?

  1. Modificás los archivos de tu proyecto local.
  2. Comprobás los cambios en tu computadora.
  3. Ejecutás git add.
  4. Creás un nuevo commit con git commit.
  5. Subís los cambios mediante git push.
  6. GitHub Pages vuelve a procesar la fuente configurada y publica la nueva versión.

Errores frecuentes:

  • El archivo index.html no está en la ubicación utilizada como fuente de publicación.
  • Se seleccionó una rama o carpeta diferente de aquella donde están los archivos del sitio.
  • Las rutas hacia CSS, JavaScript o imágenes son incorrectas.
  • Se utilizaron rutas absolutas que funcionan localmente pero no en el sitio publicado.
  • Los cambios todavía no fueron enviados al repositorio mediante git push.
  • El sitio utiliza tecnologías de backend que GitHub Pages no ejecuta como un servidor tradicional.

Flujo completo: crear web → crear repositorio → subir archivos → configurar Pages → publicar → modificar → commit → push → actualizar.

Importante: GitHub Pages permite publicar principalmente sitios estáticos. Si tu proyecto necesita ejecutar código del servidor, conectarse directamente a una base de datos o utilizar un backend propio, tendrás que utilizar una plataforma que proporcione esas capacidades.
